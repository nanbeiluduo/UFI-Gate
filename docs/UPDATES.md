# 服务更新与消息通知

## 安装器与服务版本

从 v1.0.10 开始，日常升级入口是独立后台的「更新管理」。安装器仍按每个 Release 生成对应版本、对应架构的 JS，供新用户安装，以及旧用户首次接入更新机制或修复安装。服务升级不修改 UFI-TOOLS 已保存的 JS；安装器版本与正在运行的服务版本可以不同。

**v1.0.9 及以前的用户必须先换用新版 JS 安装一次。** 老 JS 不会自动获得防降级能力，请删除旧插件条目，导入新版、保存并刷新。不要删除 `/data/ufi-gate`。此后通常只需在独立后台升级。

新版安装器先读取本地版本，检查 GitHub 最新正式版本并展示比较结果。本地版本高于内嵌版本时拒绝覆盖；相同版本需确认修复安装。无法连接 GitHub 时仍可离线安装内嵌服务，本地防降级检查继续执行。无法识别本地版本时拒绝覆盖。旧服务不支持版本查询时，依据状态文件中的最近启动版本并明确提示；没有启动记录则需要人工排查，不猜测版本。

点击确认后，只先写入随机命名的暂存目录，再启动独立安装进程。该进程取得与后台更新共用的文件锁，重新检查本地版本，因此两个入口不能同时安装。安装不会依赖宿主页面一直打开。菜单中的「查看更新状态」读取任务状态和最近更新日志。

## 后台更新

1. 登录后台，进入「更新管理」，点击「检查更新」。默认不自动检查；可开启每日自动检查，自动检查只通知，不自动安装。
2. 查看当前版本、架构、最新正式版本、发布时间说明与检查结果。每次检查至少间隔 30 秒。当前仅使用 `nanbeiluduo/UFI-Gate` 的 GitHub latest 正式 Release，不接受自定义更新源或测试版本。
3. 清单签名验证通过且目标版本更高时，可以确认安装。目标架构、协议和最低服务版本也必须兼容。协议不兼容时需换用新版 JS。
4. 服务端下载更新包，验证签名清单中的大小和 SHA-256，只解包三个规定文件，再运行候选二进制核对版本和架构。下载、校验失败不停止原服务。
5. 独立更新进程备份服务，停止旧服务，保存停止后的最终状态，替换文件并启动。通过仅本机 Root 可访问的 Unix 控制口检查实际运行版本和就绪状态。
6. 更新期间后台可能断开；稍后重新打开并登录。**更新会关闭认证开关，请核对配置后手动开启。** 停止认证期间恢复原有网络规则。

安装失败会尝试恢复旧文件及停止后保存的状态。中断记录保存在 `update-journal.json`，新版 supervisor 的启动/开机入口会尝试恢复。若磁盘、固件、启动脚本或进程本身异常导致恢复也失败，在宿主 Root Shell 运行紧急恢复脚本并检查日志。任何自动恢复都不能代替首次升级时的真机验收。

### 设备上的文件

| 文件 | 用途 |
| --- | --- |
| `ufi-gate` | 服务、后台页面、认证页面及默认 Logo，网页资源嵌入二进制 |
| `service.sh` / `emergency-recover.sh` | supervisor 与紧急恢复 |
| `state.json` | 管理员、设备、配置、配额、流量、消息及推送偏好；升级保留 |
| `bootstrap.json` | 首次安装的接口/网关；已有状态不被其覆盖 |
| `update-stage-*` | 下载/上传暂存文件；成功安装后清理本次暂存目录 |
| `update-backup/` | 最近一次安装的旧服务文件和停止后的状态快照；不要公开上传 |
| `update-runner` / `update.lock` | 独立更新程序与安装互斥锁 |
| `update-status.json` / `update-journal.json` | 可查看的任务进度 / 中断恢复记录 |
| `update.log` / `release-cache.json` | 更新进程日志 / 最近检查结果 |

更新包不会携带用户配置、管理员凭证、设备记录或自定义图片。失败的暂存目录可能保留用于排查；不要在更新过程中手动删除这些文件。`kick.go` 等源码不部署到设备，服务代码由二进制整体替换。

## 消息盒子与外部推送

认证后的全部后台页面显示右下角悬浮消息按钮，包括未读数量；登录页、初始化页和访客认证页不显示。打开后可筛选全部、未读、版本更新或设备异常消息，全部标记已读，或跳转对应管理页面。保留最近 300 条，已读状态重启后保留。

覆盖通知：上网申请、连续认证失败、配额达到 80%、流量达到上限、运行异常、管理员变更、新版本、更新结果/失败、外部推送失败。这里的运行异常指服务能够检测并记录的异常，并不保证捕获设备断电等无法写入日志的故障。

在「消息推送」配置已有企业微信、飞书、Webhook 或 SMTP 通道，再设置各类消息是否对外推送。默认对审批、配额耗尽、服务异常、更新失败开启推送选择；未配置通道时仅站内记录。审批仍保留有效期与同意/拒绝链接。

重复事件按类型和内容在 10 分钟内合并；版本与更新结果另有去重。每条待推送消息最多尝试 3 次，失败间隔 30 秒、60 秒。已结束的审批不再重试。关闭某类推送会取消该类尚未发出的消息。推送失败只生成站内提醒，避免递归推送。进程崩溃发生在外部已接收但本地尚未保存结果之间时，恢复后可能重复发送一次。

## 发布者：首次配置签名

正式发布需要一次性创建 Ed25519 密钥。下面的命令在项目根目录执行，把输出目录放在仓库外：

```powershell
go run -mod=vendor ./tools/update-sign --generate D:\Desktop\UFI-Gate-update-keys
```

目录中生成两个文件：

- `update-signing-key.txt`：私钥种子，仅将其内容添加到 GitHub 仓库的 **Settings → Secrets and variables → Actions → New repository secret**，名称为 **`UPDATE_SIGNING_KEY`**。不要上传此文件、不要粘贴到讨论或日志中。
- `update-public-key.txt`：公钥，可用于核对签名。构建器会从 Secret 派生并嵌入公钥，不需要手工改源码。

请离线备份私钥，后续版本继续使用同一把密钥。直接换密钥会使已安装服务拒绝新版本签名，需要先通过可信新版 JS 重新建立信任。本地普通构建不设置密钥也可用于开发和首次离线安装，但不能进行签名在线更新；不要将无签名开发包当作正式 Release。

## GitHub Actions 与附件

新增对应 `docs/releases/vX.Y.Z.md`，更新源码/README 版本，然后打 `vX.Y.Z` 标签触发发布；手动触发也必须填已存在的标签。工作流检出该标签的代码，构建时把标签版本注入二进制和 JS，不再在 detached HEAD 上自动提交回主分支。

正式构建强制检查签名 Secret，并同时产出：

- `UFI-Gate-X.Y.Z-arm32.js`、`UFI-Gate-X.Y.Z-arm64.js`；
- `UFI-Gate-X.Y.Z-arm32-update.tar.gz`、`UFI-Gate-X.Y.Z-arm64-update.tar.gz`；
- `update.json`、`update.json.sig`；
- 源码 ZIP、`build-info.json`、`SHA256SUMS`。

`update.json` 的 Ed25519 签名绑定版本、架构、协议、最低版本、文件名、大小和散列值。不能只上传 JS 后宣称支持后台一键更新。缺少签名或附件时，后台显示原因并禁用安装。

CI 使用临时测试密钥验证完整构建，不使用正式私钥。发布工作流使用仓库 Secret，先创建草稿、上传所有附件，再公开发布。测试包含逻辑/竞态检查、安装器测试、浏览器交互，以及 QEMU 下的 ARM 测试；实际固件上的 Root、iptables、进程守护和重启恢复仍需设备验收。
